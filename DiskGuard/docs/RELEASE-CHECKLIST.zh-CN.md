# 发布与验收检查表

## 当前状态与发布原则

本轮改动在独立验证分支上验证，因此历史 v0.2.1 的绿色 CI **不验证本轮代码**。新加入的 Rust、产品策略 VM、安全扫描与打包改动须在新提交 CI 通过后才可标记已验证。Win10/Win11 客户端项目仍保持“待执行”。

标签工作流现在默认使用 `--prerelease`，避免把 Server VM 通过等同于客户端正式验收；不会修改已发布版本。稳定发布前必须完成下面各项并人工审阅证据，再单独修改发布策略，不能仅把标记改成“通过”。

## 1. 代码与自动检查

- [ ] 审阅 diff；不修改 Sandboxie core、原生协议或共享模板。
- [ ] `npm ci`、`npm run build`、`npm test`、`npm run test:ui` 全部通过。
- [ ] Rust 固定工具链的 fmt、clippy、全部单元测试通过，包括服务失败、写盘失败和日志恢复测试。
- [ ] npm audit、RustSec 和新的 JS/Actions CodeQL 通过；新增扫描不代表旧 CodeQL 工作流已重新启用。
- [ ] 审阅扫描警告和 Windows 实际依赖图，参考 [DEPENDENCY-REVIEW.md](DEPENDENCY-REVIEW.md)；退出码为零不等于没有信息级告警。
- [ ] 安装包和便携包在全新 hosted VM 中通过官方运行时部署、篡改拒绝、幂等安装、原生适配器和产品策略探针。
- [ ] 产品策略探针确实调用 Backend 保存/应用，再证明黑名单读取/枚举阻断、相邻目录不误封、强制入箱、子进程、重启持久化、规则停用和删除。
- [ ] 运行日志与失败证据可下载；发布记录附对应提交和运行 URL。临时 Artifact 过期前，把脱敏验收报告归档到独立受控存储。

## 2. Windows 客户端验收（不可由云端 Server 替代）

为 Windows 10 x64 和 Windows 11 x64 各准备一次性 VM 快照，保留系统签名强制和安全启动。记录具体版本/构建，而不只写“Win11”。不在日常电脑运行驱动测试。

每个平台分别验证安装/卸载/WebView2、便携、标准用户、UAC 接受与拒绝、重启、断网、已有 Classic/Plus、服务停止、中文/长路径/网络盘/重解析点、托盘、开机启动和高日志量。白名单分别验证有授权/无授权与模板冲突；QQ/微信分别记录版本、登录、消息、收发文件、更新与重启。

可在准备好的隔离 VM、管理员 PowerShell 7 中运行：
```powershell
./DiskGuard/scripts/Test-Runtime.ps1 -AcknowledgeDisposableVm
```
它验证上游行为，不替代手工 UI 流程。`Test-ProductPolicy.ps1` 和产品测试 CLI 只允许 hosted 一次性 Windows VM，不要伪造环境变量在宿主机运行。

每项证据至少记录：日期、测试人、系统构建、应用/运行时版本、源提交、步骤、预期、实际、通过/失败/未执行、脱敏证据位置。失败不能写成跳过后通过。将结果填回 `VALIDATION.md` 对应矩阵，并保留原始测试输出。

可先用只读收集器生成环境信息与全部为 `not_run` 的验收模板：
```powershell
./DiskGuard/scripts/New-ClientAcceptanceReport.ps1 -EvidenceDirectory C:\DG-Acceptance\Win11-Run1 -Application C:\Path\DiskGuard.exe
```
脚本不会安装驱动或启停服务，也不会推断任何场景通过；Server 会被明确拒绝。输出可能含实际安装路径，上传前脱敏。

## 3. GitHub 保护（需要仓库管理员执行）

以下是设置清单，不代表已修改远程仓库：

1. Settings → Rules → Rulesets，为 `diskguard` 分支增加规则，要求 PR、禁止强制推送/删除，按维护团队实际设置审批与绕过权限。
2. 新工作流至少成功运行一次后，要求状态检查 **DiskGuard quality gate**，并核对 GitHub 实际显示的检查名称。路径过滤不会覆盖无关上游文件；无关 PR 若因此等待必需检查，应手动运行对应分支的 DiskGuard 工作流，或调整为所有 PR 均运行，不能绕过检查。
3. 对 `diskguard-v*` 标签限制创建/更新/删除，只允许受信维护者发布。
4. 保持默认工作流只读权限，不为解决扫描或发布错误而授予全仓库写权限。
5. 在仓库启用 Actions、代码扫描等所需功能，并实际确认新的 `diskguard-security.yml` 可以运行。不要为本项目盲目重启与 Fork 无关的上游发布任务。

## 4. 发布者签名（需要真实证书或受信签名服务）

当前未增加占位私钥，也没有自动下载任何证书。稳定分发前应选择受信 Authenticode 签名方案，将凭据放在受保护环境/密钥服务中，不进入仓库或普通 Artifact。

正确顺序：编译 → 给应用 EXE 签名并加可信时间戳 → 生成安装包/便携包 → 给安装包签名 → 校验应用和安装器签名 → 重新计算清单/校验和 → 测试**最终签名包** → 发布。不改写已签名官方运行时；现有 Build.ps1 在未签名路径上工作，引入签名时需要显式调整打包顺序，不能在发布后改包。

## 5. 最后发布

- [ ] 所有外部条件与客户端证据完成，不含“待执行”冒充通过。
- [ ] 更新版本和变更日志，标签与配置一致；正式发布需单独审阅签名管线。
- [ ] 在获得明确授权后提交、推送新提交；检查新提交的质量门禁和 VM 证据。
- [ ] 在获得明确授权后创建并推送新版本标签；不得复用旧标签覆盖已有资产。
- [ ] 校验发布页面下载的最终产物、SHA256SUMS、构建清单和安装行为。
- [ ] 发布说明准确区分 UI 无签名/官方驱动签名、客户端验收和云端验证范围。

在没有管理员权限、签名凭据或客户端 VM 证据时，最后三类事项应明确保留未完成，而不是声称已正式发布。
